Aguardando aprovação MCP / CDP / Codex 2026-06-25

Gateway MCP para os navegadores CDP

Trocar quatro MCPs Playwright pesados por um daemon local leve, com workers recriáveis por perfil. A ponte do Codex fica viva; a memória pesada pode dormir.

Decisão: implementar primeiro um gateway HTTP com aliases compatíveis para os nomes atuais. Só depois migrar as skills para um namespace único gabriel-browsers.

O Que Muda

  • Antes Cada perfil usa seu próprio @playwright/mcp. Matar esse processo libera RAM, mas corta o transporte da thread e causa Transport closed.
  • Depois Um daemon local fica vivo. Ele cria workers por perfil quando alguma ferramenta é chamada e mata apenas esses workers quando ficarem ociosos.
  • Fora do escopo Não mexer em default browser, LaunchServices ou no comportamento de roteamento de links do app.

Mapa do Plano

Backup e inventário

Salvar a configuração atual e mapear skills/processos antes de tocar no fio.

Resultado: rollback pronto e baseline de RAM.
Wave 1

Daemon seguro

Criar o gateway HTTP local com health check, autenticação e LaunchAgent.

Resultado: processo pai leve e sempre vivo.

Adicionar workers Playwright por perfil, idle timeout, leases e restart automático.

Resultado: RAM cai sem perder ferramentas.

Preservar os nomes antigos no Codex enquanto o backend passa a ser o gateway.

Resultado: arquitetura limpa, com rollback preservado.

Entregáveis

  • Backup seguroConfig atual preservada antes de qualquer alteração.
  • Gateway localServidor MCP HTTP leve em loopback, com autenticação.
  • Workers recriáveisPlaywright/CDP nasce sob demanda e morre por idle.
  • CompatibilidadePrefixes antigos seguem disponíveis durante a migração.
  • App ajustadoLimpeza passa pelo gateway, não por kill direto de PID.
  • Skills atualizadasUso final via profile no MCP único.

Riscos Que Importam

  • Alto Gateway desligado no startup.
    Sem daemon vivo, o Codex não vê tools HTTP. Mitigação: LaunchAgent obrigatório com health check.
  • Alto Discovery carregando Playwright.
    Se listar tools cria workers, a economia de RAM vira teatro. Mitigação: schemas estáticos e teste específico.
  • Médio Múltiplas threads no mesmo perfil.
    Uma thread não pode matar o worker da outra. Mitigação: leases, mutex e cleanup sem chamada em voo.
  • Médio Segurança local.
    O gateway controla perfis logados. Mitigação: bearer token, loopback e endpoints admin protegidos.

Critérios de Aceite

  1. 1 Nova thread do Codex mostra ferramentas MCP sem abrir quatro workers Playwright pesados no startup.
  2. 2 Worker morto por idle é recriado na próxima chamada sem Transport closed.
  3. 3 Pessoal, ES, RJ e Financeiro/CentralSP continuam abrindo no perfil certo.
  4. 4 Rollback para a configuração atual é simples e testado.
  5. 5 Build e testes do app passam se a UI/Swift forem alterados.

Revisão Crítica

Foram encontrados gaps críticos/altos e o plano mudou por causa deles: preservar namespaces antigos na primeira fase, impedir spawn pesado em tools/list, adicionar leases por sessão, autenticar o gateway e tornar a integração do app obrigatória.
